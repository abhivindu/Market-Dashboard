# Wishlist — deferred items pending paid/better data access

Items below are things we'd add or improve if paid/institutional data access becomes available. Not built into v1 because free-tier data can't support them reliably.

## Data sources
- **Bloomberg Terminal / FactSet / S&P Capital IQ (sp-global plugin)** — real fundamentals, real-time quotes, consensus estimates. Would replace Yahoo Finance scraping and manual WebSearch estimate-gathering.
- **LSEG/Refinitiv (`lseg` plugin, claude-for-financial-services marketplace)** — bond pricing, yield curves, FX carry, options valuation. Correct tool for Point 4 (fixed income) once available.
- **MarketChameleon / Unusual Whales / CBOE DataShop** — real single-name options volume/OI spike detection. Currently approximated with free aggregate-only signals (VIX term structure, CBOE total put/call ratio) — no per-stock granularity.
- **Crunchbase / PitchBook** — structured private-company funding round data for Point 2 (trend monitor) drilldowns. Currently sourced via WebSearch news mentions only — less complete, less structured.
- **CoinPaprika MCP** (`coinpaprika/claude-marketplace`, free, not installed) — crypto/DeFi market data. Only relevant if a crypto shock is driving Point 1's "other markets" trigger, or if Point 2 grows a dedicated crypto/blockchain-infra sector. Skipped for v1 since WebSearch fallback already catches shocks large enough to matter.
- **Paid free-tier upgrades** (Alpha Vantage, Financial Modeling Prep, Finnhub) — would need account signup + API key from user. Not required for v1; current free/unauthenticated sources (Yahoo Finance query endpoints, FRED CSV, NASDAQ Trader symbol directory, SEC EDGAR) cover Phase 1 scope.

- ~~Real fundamentals (trailing/forward P/E) for the value bucket~~ — **IMPLEMENTED 2026-09-22**: `build_recommendations.py` pre-screens the full universe with the existing 52wk-discount proxy (still needed at 1,500-ticker scale), then fetches real `trailingPE`/`forwardPE` via yfinance `.info` for just the top `TOP_N*3` (15) most-discounted survivors — a small, safe shortlist, not the full universe. The final 5 value picks are now ranked by lowest real trailing P/E among that shortlist (falling back to the discount ranking to fill slots if fewer than 5 have usable PE data), and the stat now renders on each value-bucket card in Point 3. EV/EBITDA and full-universe-scale fundamentals are still out of reach for free (that part of the original ask stands) — see the entry below.
- **EV/EBITDA and full-universe-scale fundamentals** — still genuinely needs a paid API (FMP, Alpha Vantage premium) or Yahoo `.info` calls at 1,500-ticker scale, which stays slow/rate-limit-prone even after the value-bucket fix above (that fix works specifically because it's scoped to a ~15-name shortlist, not the full universe).

## Known data-freshness gaps (free tier)
- **yfinance bulk equity-history lag** (first encountered 2026-09-22 pull) — the free Yahoo Finance `yf.download` bulk endpoint `fetch_price_history.py` uses for the ~1,500-name universe can lag a full trading day behind the individual index tickers (`^GSPC`, `^IXIC`, etc.) `fetch_indices.py` pulls separately. On the first 2026-09-22 pull, run ~4.5 hours after Monday's close, every individual-equity daily bar was still `NaN` for Monday while the index tickers already had Monday's close — so Point 3's movers/gainers/losers table initially reflected Friday's session even though Point 1's index-level flags were already Monday-fresh (a later same-day re-pull, ~2 hours on, caught up once Yahoo did). **Now mitigated in code, not just docs**: `fetch_price_history.py` compares its own data's as-of date against `indices.json`, retries once, and sets a `stale` flag (`data/point3/aggregates.json`'s `equity_data_stale`) that `build_final_payloads.py` surfaces as an automatic freshness-note caveat when no hand-written override exists — see CLAUDE.md's "Equity-data freshness self-check" section. This doesn't eliminate the underlying Yahoo lag (a paid fundamentals/price API would), just makes it visible and self-documenting instead of a silent multi-hour trap a curator has to notice by hand; still re-run `fetch_price_history.py` later in the day if `equity_data_stale` comes back `true` and today's exact movers matter.
- **FRED's DCOILWTICO (WTI, EIA-sourced) series lag** (encountered same 2026-09-22 pull, worse than the equity one) — unlike the Fed-published Treasury/spread series (reliably ~1 day behind), FRED's WTI series hadn't published a new point in a full week (last published 2026-09-15, still true when re-checked mid-session on 2026-09-22). Point 1's `oil_move` materiality flag was silently re-firing on the exact same stale value pull after pull — the flag's narrative looked "dated" not because research was skipped, but because the underlying data point genuinely hadn't moved, so per the citation-date discipline there was nothing new to write about. The masked reality: WTI had actually fallen ~13% (Saudi crude exports rerouted through the Strait of Hormuz, US-Iran diplomacy hopes around the UN General Assembly), the opposite direction of the stale flag's framing. **Now mitigated in code**: `fetch_macro.py` checks `DCOILWTICO`'s staleness (>3 calendar days) and falls back to Yahoo Finance's WTI futures (`CL=F`) for `last_value`/`last_date`/`day_chg`/`month_chg` when it fires — the same free-data pattern gold/silver already use (FRED's own gold/silver series were discontinued). The sparkline `history` stays FRED's own series through its last published point (no mixing quote types); the swapped-in fields get a `price_source: "yahoo_fallback_cl=f"` tag plus `fred_last_date`/`fred_last_value` for transparency. Only `DCOILWTICO` is covered so far — if another FRED series (a spread, a rate) is ever observed lagging this badly, extend the same `days_stale()` check to it rather than assuming it's Treasury-series-reliable forever.
- **`market_caps_cache.json` had no automatic staleness gating** (found in a 2026-09-22 full-pipeline audit) — the script's own docstring said "run roughly weekly" but nothing actually checked whether a week had elapsed; whether it got refreshed depended entirely on a human/agent noticing and deciding to run it, with no enforcement, so it could in principle go stale indefinitely (silently degrading the $2B+ cap filter and sector-cap-weighting) without ever showing up as an error. **Fixed**: `fetch_market_caps_cache.py` now checks its own cache's age on every invocation and skips the slow ~10-15 min refetch if it's under `MAX_CACHE_AGE_DAYS` (7), refreshing automatically otherwise (or with `--force`). CLAUDE.md's pipeline list now says "self-gating, safe to always run" instead of "weekly is enough" — the routine no longer needs to make that judgment call itself.

### 2026-09-22 full-pipeline data-freshness audit — everything else checked and confirmed fine
Went through every `fetch_*.py`/`build_*.py` script and every FRED series this pipeline reads, looking for the same class of silent-staleness bug as the two above. Findings, so a future session doesn't have to re-investigate:
- `fetch_indices.py`, `fetch_universe.py`, `fetch_earnings_calendar.py` — all hit a live endpoint fresh on every run with no caching layer; no staleness risk.
- VIX/VIX9D/VIX3M (`fetch_vol_term_structure` in `fetch_macro.py`) and Gold/Silver (`fetch_yahoo_commodity`) — individual `yfinance.Ticker().history()` calls (not the bulk `yf.download` path that caused the Point 3 equity lag); confirmed fresh (1-day lag, as expected) both times checked this session.
- The other FRED series (`DGS3MO`, `DGS2`, `DGS10`, `DGS30`, `DFF`, `SOFR`, `T10Y2Y`, `T10Y3M`, `BAMLC0A0CM`, `BAMLC0A4CBBB`, `BAMLH0A0HYM2`, `DTWEXBGS`) — these show larger calendar-day lags than DCOILWTICO ever did pre-incident (1-4 days depending on the series; `DTWEXBGS` specifically is a **weekly** Fed H.10 release, so a ~7-day gap there is normal, not a bug). Confirmed via direct `fredgraph.csv` fetches and by diffing this pull's `macro.json` against the prior pull's (committed at `d62fc56`) that every one of these series genuinely *advanced* to a new date/value between pulls — unlike `DCOILWTICO`, which was frozen on the exact same value for a full week. No fallback added for these; they don't need one, and adding a Yahoo-quote fallback for Treasury Constant Maturity yields would risk mixing incompatible methodologies for no real benefit.
- Point 2 (`data/point2/sectors.json`) and Point 4 (`data/point4/asset_classes.json`) have no mechanical fetch step at all — every field is hand-researched via WebSearch during the pull's manual step (CLAUDE.md's daily-routine steps 3-4). There's nothing to audit in code for these; their freshness depends on that manual step actually happening each pull, which is a discipline question, not a pipeline bug.
